Snowflake porta i Coding Agent nei Server MCP Gestiti

Dal 23 ottobre 2026 i server MCP gestiti da Snowflake possono esporre un tool CODING_AGENT senza oggetto agent: thread, sandbox, flag e limiti documentati.

Vivacity AI Division  ·  Ottobre 2026  ·  Alessandro Demontis

I. Un coding agent senza oggetto persistente

La release note di Snowflake del 23 ottobre 2026, intitolata «Coding agent MCP tool», introduce una novità nei server MCP gestiti dalla piattaforma. Un server può ora esporre un coding agent senza che esista un agente memorizzato come oggetto Snowflake. Finora un agente richiamato via MCP doveva essere definito a parte e referenziato. Ora il tool si dichiara direttamente nella specifica del server.

Il punto è architetturale. Il proprietario del server non crea prima un oggetto agent e poi lo collega: descrive nella configurazione stessa del server il tool, con i parametri che vuole controllare. La semplificazione riguarda la dichiarazione. Non va letta come un workflow di sviluppo già pronto.

In sintesi: la fonte documenta un nuovo tipo di tool e il suo comportamento. Non documenta la qualità del codice prodotto, i costi o le prestazioni. Modello, istruzioni e tool restano scelte di chi configura il server.

II. CODING_AGENT: come si dichiara in un server MCP

Nel server specification in formato YAML si aggiunge un tool con type CODING_AGENT. Il campo identifier si omette, perché serve ai tool che puntano ad altri oggetti Snowflake e qui non c'è nulla da referenziare.

La configurazione è opzionale e comprende model, instructions, tools, tool_resources e skills. Le fonti non indicano un modello predefinito, quindi non va dato per scontato. Chi vuole un comportamento prevedibile deve valutare cosa specificare esplicitamente.

A ogni esecuzione Snowflake aggiunge il toolset code_toolset_all. Per questo non si può configurare nello stesso tool anche code_execution: le due opzioni non convivono. Il sandbox è descritto dalla documentazione come ambiente gestito per il coding. Non esiste, nelle fonti citate, un elenco delle sue capacità interne, e qui non se ne ricostruisce uno.

Il tipo CODING_AGENT non richiede un oggetto agent né un identifier: la definizione vive nella specifica del server.

III. Un thread, sandbox e continuità tra chiamate

Il client invia un campo text. Alla prima chiamata omette thread_id, e la risposta ne restituisce uno. Nelle chiamate successive il client lo ripassa per proseguire la conversazione e riutilizzare il sandbox associato al thread. È questo che rende possibile un lavoro in più passaggi: il contesto e l'ambiente non ripartono da zero a ogni richiesta.

Il parametro opzionale parent_message_id governa la ramificazione. Se omesso, la conversazione continua dall'ultimo messaggio. Se vale 0, si apre un nuovo ramo sul thread esistente. Si possono quindi esplorare strade alternative senza creare un thread nuovo.

Sul piano operativo conta il flag ENABLE_MCP_AGENT_RUN_THREAD_CONTINUATION, abilitato per default. Se viene disattivato, Snowflake nasconde thread_id e parent_message_id e ogni chiamata diventa una nuova esecuzione. Un client progettato per la continuità perderebbe quindi stato e sandbox. Il flag va verificato prima di costruire un flusso persistente.

Da ricordare: la continuità dipende da un flag. Con il flag attivo, thread_id e parent_message_id sono disponibili. Con il flag disattivo, ogni chiamata è un'esecuzione nuova. Le fonti non offrono altre garanzie di persistenza oltre a questo comportamento.

IV. Il confronto con gli altri tool Snowflake

CODING_AGENT è un tipo distinto nel catalogo dei tool MCP gestiti. CORTEX_AGENT_RUN richiama un agente già configurato come oggetto Snowflake. GENERIC espone UDF e procedure. SYSTEM_EXECUTE_SQL esegue SQL, mentre Cortex Search e Cortex Analyst coprono ricerca e analisi. Ciascun tipo ha un ruolo diverso, e il nuovo non sostituisce gli altri.

La differenza principale con CORTEX_AGENT_RUN è l'assenza dell'oggetto persistente. Con CORTEX_AGENT_RUN l'agente esiste nella piattaforma e il server lo richiama. Con CODING_AGENT la configurazione sta nella specifica del server. Le fonti non dicono quale approccio sia preferibile: la scelta dipende da governance e riuso.

Il protocollo resta quello MCP. Il client scopre i tool con tools/list e li invoca con tools/call. Il server gestito da Snowflake espone tool, non risorse né prompt: chi si aspetta questi altri elementi MCP non li troverà qui.

Cambia il modo di dichiarare l'agente, non il modello di interazione: scoperta con tools/list, invocazione con tools/call.

V. OAuth, RBAC e confini di sicurezza

Nella documentazione la sicurezza resta nella configurazione del server. OAuth è l'approccio raccomandato per l'autenticazione. L'accesso a server e tool è regolato dal RBAC, con il principio dei privilegi minimi per ciascun ruolo: a un ruolo si concede solo ciò che serve.

Un punto da non fraintendere riguarda le annotazioni MCP. Sono suggerimenti rivolti al client, non controlli di sicurezza. Una dichiarazione di sola lettura, per esempio, non sostituisce i privilegi effettivi assegnati al ruolo. I confini reali si costruiscono con ruoli e permessi.

La documentazione invita poi a verificare i tool di terze parti prima di inserirli nel server. Chiede anche di prevenire loop ricorsivi costosi: un agente che richiama tool capaci di riattivarlo può generare esecuzioni a catena. La fonte non fornisce meccanismi automatici in merito, quindi la prevenzione va pensata in fase di progettazione.

VI. Limiti, condizioni e cosa verificare prima dell'adozione

I limiti documentati sono due. Un server MCP può avere al massimo 50 tool. I risultati dei tool GENERIC e SQL vengono troncati a 250 KB. Chi si affida a questi tool per restituire dataset voluminosi deve tenerne conto: una risposta troncata può risultare incompleta se non progettata con attenzione.

Le fonti consultate non esplicitano alcuni elementi, che quindi non si possono affermare: un prezzo separato per questa aggiunta, un modello predefinito, uno SLA, le regioni in cui è disponibile, benchmark di qualità. Lo stesso vale per la disponibilità uniforme tra account. Per chi valuta l'adozione da Cerveteri (RM) come da qualunque altra sede, la verifica va fatta sulla propria configurazione e sulla documentazione aggiornata, non sul presupposto di una copertura omogenea.

Prima di procedere conviene controllare cinque punti:

1. lo stato di ENABLE_MCP_AGENT_RUN_THREAD_CONTINUATION, se serve continuità;
2. la configurazione di model, instructions, tools, tool_resources e skills, sapendo che code_execution non è utilizzabile insieme a code_toolset_all;
3. OAuth, ruoli e privilegi minimi, senza affidarsi alle annotazioni;
4. il numero di tool, che non può superare 50, e la gestione dei risultati troncati a 250 KB;
5. la prevenzione di loop ricorsivi e la revisione dei tool di terze parti.

Cautela editoriale: release note e documentazione descrivono funzione e configurazione, non una valutazione indipendente del coding agent. Disporre del tool CODING_AGENT non equivale ad avere un workflow end-to-end già predisposto. Prima di una messa in produzione servono prove sul proprio ambiente.
