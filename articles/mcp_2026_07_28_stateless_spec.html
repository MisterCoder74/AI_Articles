MCP Diventa Stateless: la Specifica 2026-07-28 Riscrive le Regole degli Agenti AI

MCP diventa stateless: addio sessioni e handshake. AWS contribuisce Tasks per agenti di lunga durata su Amazon Bedrock.

Vivacity AI Division  ·  Agosto 2026  ·  Alessandro Demontis

C'è un giorno in cui un protocollo smette di essere una promessa e diventa infrastruttura. Per il Model Context Protocol, quel giorno è il 28 luglio 2026.

I. 28 Luglio 2026: la Revisione Più Grande nella Storia di MCP

Non è un aggiornamento incrementale. È una riscrittura dell'assunzione fondativa. MCP nasce bidirezionale e stateful: connessioni persistenti, sessioni, handshake. Con la revisione del 28 luglio, il protocollo diventa stateless — puro richiesta/risposta, senza memoria di connessione.

Chi ha costruito server MCP negli ultimi due anni sa cosa significava prima: session affinity, storage condiviso, load balancer intelligenti che dovevano ricordarsi dove instradare ogni client. Un workload "speciale", diverso da qualunque altra API REST in produzione.

Un protocollo che dimentica la connessione, per ricordarsi meglio dello stato che conta davvero: quello dell'applicazione, non quello del socket.

La documentazione ufficiale su blog.modelcontextprotocol.io e il changelog tecnico della specifica 2026-07-28 non lasciano dubbi: ogni server MCP in produzione deve essere ripensato. Non aggiornato — ripensato.

II. Via Sessioni e Handshake: Cosa Cambia nella Richiesta

Il primo taglio è chirurgico: sparisce l'handshake initialize/initialized. Sparisce l'header Mcp-Session-Id. Sparisce ogni requisito di gestione dello stato a livello di connessione.

Al suo posto, ogni richiesta diventa autodescrittiva. Porta con sé versione del protocollo e capability del client dentro un campo _meta, con chiavi come io.modelcontextprotocol/clientInfo, /protocolVersion e /clientCapabilities. Header HTTP dedicati — Mcp-Protocol-Version, Mcp-Method, Mcp-Name — permettono routing e autorizzazione a livello di gateway senza dover aprire e parsare il corpo JSON.

Il risultato pratico è netto: qualunque richiesta può atterrare su qualunque istanza dietro un load balancer round-robin banale. Nessuno storage condiviso. Nessun sticky routing.

Con l'header Mcp-Session-Id rimosso e le sessioni eliminate a livello di protocollo, un server MCP diventa indistinguibile da un normale servizio HTTP stateless per qualunque gateway, WAF o rate limiter già esistente.

E se serve stato che attraversa più chiamate? La risposta è esplicita: gli handle vengono generati dall'applicazione e passati come normali argomenti dei tool. Lo stato viaggia con la richiesta, non con la connessione. È una scelta di design che sposta la responsabilità dallo strato di trasporto allo strato applicativo — dove, in fondo, dovrebbe sempre essere stata.

III. Multi Round-Trip Requests: Chiedere Conferma Senza uno Stream Aperto

C'è un problema che uno stateless puro non può ignorare: come chiede conferma un server durante un'operazione, se non ha più uno stream aperto verso il client? Prima, richieste come sampling/createMessage, elicitation/create e roots/list partivano dal server e vivevano dentro una connessione persistente.

La revisione introduce le Multi Round-Trip Requests. Un server che ha bisogno di dati aggiuntivi non blocca la connessione: risponde con resultType: "input_required" e un campo inputRequests. Il client, ricevuta la richiesta, la ripete includendo inputResponses con i dati necessari.

Chiedere una conferma a metà operazione, senza uno stream aperto, è come lasciare un messaggio in una bottiglia e aspettare che torni indietro con la risposta scritta sopra.

Concettualmente è semplice. Nella pratica, richiede disciplina: ogni client e ogni server devono implementare correttamente questo scambio, altrimenti l'intera classe di interazioni — conferme utente, raccolta parametri interattiva — si rompe silenziosamente in produzione.

IV. L'Estensione Tasks e il Contributo di AWS per gli Agenti di Lunga Durata

La funzionalità Tasks passa da nucleo sperimentale a estensione ufficiale, sotto il namespace io.modelcontextprotocol/tasks. Il vecchio tasks/result bloccante viene sostituito da polling tramite tasks/get. Arriva un nuovo tasks/update per l'input dal client verso il server. Sparisce tasks/list. I server possono ora restituire handle di task non richiesti.

Il dettaglio che conta di più, però, è chi ha contribuito questa estensione: AWS. Non è un dettaglio da footnote. Segnala che i grandi cloud provider non stanno solo adottando MCP — lo stanno attivamente forgiando per i propri casi d'uso enterprise.

L'estensione Tasks abilita lavoro asincrono di lunga durata affidabile su server MCP distribuiti su Amazon Bedrock AgentCore, che ha integrato la specifica 2026-07-28 fin dal lancio. Per chi progetta agenti che devono completare operazioni lunghe — ricerche multi-step, orchestrazioni complesse, elaborazioni batch — questo cambia radicalmente cosa è possibile costruire su infrastruttura standard, senza gestione manuale delle sessioni.

Come parte del framework di estensioni, viene stabilita formalmente anche MCP Apps: interfacce utente interattive consegnate in iframe sandboxati, integrate con l'architettura stateless per esperienze scalabili senza compromettere l'isolamento.

V. Cache, Autorizzazione e gli Altri Dettagli che Contano in Produzione

Sotto la superficie, ci sono modifiche che decidono se un sistema regge il traffico reale o crolla al primo picco. I risultati di tools/list, prompts/list, resources/list e resources/read ora includono ttlMs e cacheScope ("public" o "private"), permettendo alle cache intermedie di prendere decisioni informate. Meno re-fetching inutile, cache hit rate più alto sui prompt a monte.

La validazione dell'issuer secondo RFC 9207 e il passaggio da Dynamic Client Registration a Client ID Metadata Documents chiudono una falla nota: credenziali client ora legate esplicitamente al server di autorizzazione emittente.

C'è anche una piccola rivoluzione silenziosa per chi sviluppa app desktop e CLI: eliminati gli errori di redirect_uri, grazie alla corretta specifica di application_type. Un dettaglio minore sulla carta, una frustrazione tolta di mezzo per chiunque abbia debuggato flussi OAuth alle tre di notte.

VI. I Numeri dell'Adozione e Cosa Significano per Chi Sviluppa Oggi

I numeri raccontano una traiettoria che pochi protocolli riescono a percorrere così in fretta. I quattro SDK di primo livello — TypeScript, Python, Go e C# — sono passati da 97 milioni di download mensili a marzo 2026 a quasi 500 milioni di download al mese. Sia l'SDK TypeScript che quello Python hanno superato il miliardo di download totali. L'SDK Rust supporta già la nuova specifica in beta.

Da 97 a 500 milioni di download mensili non è crescita: è un protocollo che smette di essere una scommessa e diventa il modo in cui gli agenti parlano con il mondo esterno.

Tutti gli SDK sono stati rilasciati simultaneamente, con guide di migrazione dedicate ai breaking change, e una finestra minima di deprecazione formalizzata a 12 mesi — un margine di respiro per chi deve pianificare la migrazione senza fermare la produzione.

Il supporto immediato è arrivato da Microsoft, Google Cloud, AWS, Anthropic, Cloudflare, Figma, Netlify, Xero, oltre a framework specializzati per agenti come FastMCP, Horizon e Runlayer. Non è adozione simbolica: è un intero ecosistema che riallinea la propria infrastruttura attorno a un unico standard stateless.

Per chi sviluppa server MCP oggi, il messaggio è chiaro: una classe intera di problemi operativi — session affinity, storage di sessione distribuito, sticky routing — scompare. Il prezzo da pagare è ripensare esplicitamente ogni pezzo di stato che il proprio server manteneva tra una chiamata e l'altra. Non è un lavoro banale, ma è un lavoro che, una volta fatto, restituisce un server MCP scalabile come qualunque altra API HTTP — niente di più, niente di meno.
