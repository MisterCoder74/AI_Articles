VS Code 1.145: agenti diversi nella stessa sessione di coding

VS Code 1.145 introduce in Preview le nested agent sessions con harness diversi nella stessa sessione principale: ogni chat conserva modello, agente e permessi propri.

Vivacity AI Division  ·  Novembre 2026  ·  Alessandro Demontis

I. Una sessione, più harness

Il 4 novembre 2026 è uscita la versione Stable 1.145 di Visual Studio Code. Tra le novità sul lavoro con gli agenti, le note ufficiali ne indicano una dal titolo eloquente: Mix and match agent harnesses in one session. Il senso è semplice: dentro una stessa sessione principale si possono avere chat annidate che usano harness diversi da quello della sessione di partenza.

L'esempio documentato è concreto. Si può chiedere a Claude di rivedere un piano scritto in una chat Copilot, oppure affidare lo stesso compito a Codex. Le conversazioni restano raggruppate nella sessione principale, senza finire in contesti separati e scollegati.

In breve: la funzione è in Preview e si controlla con l'impostazione chat.agentHost.multipleChatProviders.enabled. Le note non parlano di disponibilità generale.

II. Come funzionano le nested sessions

Una nested session è una sessione annidata dentro una sessione parent. La novità della 1.145 sta in una possibilità precisa: la nested session può selezionare un harness diverso da quello del parent. In passato il parent definiva il quadro, ora una chat figlia può uscirne.

Il caso d'uso descritto è la revisione incrociata. Un piano nasce in una chat, poi un'altra chat, con un altro harness, lo rilegge o lo riprende, mentre il lavoro resta ordinato nella stessa sessione principale. Il raggruppamento è il punto centrale: la sessione principale fa da contenitore e le chat annidate ne fanno parte, anche se poggiano su harness diversi.

«Mix and match agent harnesses in one session»

Titolo della funzione, dalle note di rilascio di Visual Studio Code 1.145.

Le note non descrivono altri meccanismi interni. Non dicono come gli harness si scambino informazioni, né se condividano strumenti o stato. Quello che si può affermare è ciò che i documenti attestano: le conversazioni stanno insieme nella sessione principale, mentre la configurazione di ciascuna resta separata, come spiegato nella prossima sezione.

III. Modello, agente e permessi restano distinti

Questo è il passaggio da leggere con più attenzione. Secondo le note, ogni chat mantiene il proprio modello, il proprio agente e i propri livelli di permesso, e questi valori sono determinati dal suo harness. Una nested chat con un altro harness non eredita quindi automaticamente le scelte del parent.

Vale anche l'inverso: cambiare questi valori in una chat non modifica le altre. Se si regola il modello o il livello di permesso in una conversazione, le altre restano come sono. Per chi gestisce più chat nella stessa sessione, questo significa poter calibrare ogni conversazione senza effetti collaterali sulle altre.

Da tenere presente: la separazione di modello, agente e permessi è dichiarata esplicitamente. Non è invece dichiarata alcuna condivisione di stato, strumenti, modello o permessi tra harness diversi, quindi non va presupposta.

Raggruppare chat in una sessione non equivale a unificarne le impostazioni. Le note non affermano nemmeno che gli harness abbiano capacità equivalenti: la funzione permette di combinarli, non di renderli intercambiabili.

IV. Cronologia, spostamento e fork

La gestione delle sessioni segue lo stesso principio di continuità. Quando una chat viene spostata, conserva la propria cronologia e prosegue con l'harness che era stato selezionato. Lo spostamento riorganizza il lavoro, ma non reimposta la conversazione né la cambia di harness.

Per il fork le note indicano che la sessione derivata mantiene la stessa configurazione. Chi vuole esplorare una variante di un'attività ha quindi un punto di partenza coerente con l'originale.

In sintesi, secondo le note: una chat spostata mantiene cronologia e harness selezionato; una sessione forked mantiene la stessa configurazione.

Sintesi dei contenuti delle note di rilascio di VS Code 1.145, non citazione testuale.

C'è poi un dettaglio di leggibilità. Quando una chat usa un harness diverso da quello del parent, il nome dell'harness compare passando il puntatore sulla tab o sulla riga corrispondente nella lista delle sessioni. Con più chat annidate, permette di capire a colpo d'occhio quale harness stia lavorando dove.

V. Impostazione e flusso pratico

Il primo passo è l'impostazione. La funzione non è attiva per impostazione predefinita, almeno secondo quanto emerge dalle note: richiede chat.agentHost.multipleChatProviders.enabled. Senza di essa non si può contare sul comportamento descritto.

Dalle note si ricava questo flusso generale:

1. Attivare l'impostazione indicata.
2. Lavorare in una sessione principale, per esempio con una chat Copilot in cui si è scritto un piano.
3. Aprire una nested session scegliendo un harness diverso, per esempio Claude o Codex, per rivedere il piano o svolgere lo stesso compito.
4. Riconoscere le chat nella lista sessioni, passando il puntatore su tab o riga per vedere l'harness quando differisce dal parent.
5. Regolare modello, agente e permessi chat per chat, ricordando che ogni modifica vale solo per la conversazione in cui si fa.

Le note non dettagliano le voci di menu né i passaggi dell'interfaccia, e questo articolo non li inventa. Per l'elenco esatto dei controlli, la fonte da consultare resta la pagina ufficiale della versione 1.145.

VI. Preview e limiti da non oltrepassare

La funzione è in Preview. Questo la colloca in una fase in cui comportamento e rifinitura possono ancora cambiare, e la sua disponibilità concreta dipende dall'impostazione citata. Le note non dichiarano disponibilità generale né indicano piani o condizioni particolari: nessuna di queste informazioni va quindi data per assodata.

Ci sono altri limiti di metodo. La fonte è la documentazione ufficiale del prodotto, non un benchmark indipendente: descrive cosa la funzione consente, non quanto sia efficace nell'uso reale. Non si può dedurre che un cambio di harness porti con sé stato, strumenti, modello o permessi dell'altro, né che gli harness offrano le stesse capacità o interoperino oltre quanto scritto.

Nello stesso rilascio compaiono altre novità, come le automazioni locali con espressioni cron a cinque campi e gli agenti custom del workspace. Sono funzioni distinte, che qui restano fuori. Lo stesso vale per gli annunci di GitHub su Copilot in JetBrains Air e Xcode, che riguardano altri prodotti.

Cosa resta: più harness nella stessa sessione, con modello, agente e permessi separati per ogni chat. Dato lo stato di Preview, conviene provarla con questo perimetro e senza aspettative non documentate.

Per chi lavora con più agenti, VS Code 1.145 offre quindi un'idea chiara: tenere insieme le conversazioni senza confondere le configurazioni. Quanto sia utile nella pratica lo diranno l'uso e l'evoluzione della funzione oltre la fase Preview.
